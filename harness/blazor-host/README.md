# Blazor Web App test host

honua-studio#5's Phase 0 adversarial finding (P1-4): a bare static host page
cannot reproduce the hazards Honua Console's `/studio` embed will actually
face, because console is a Blazor Web App with enhanced navigation and
interactive render modes — SSR/enhanced-nav DOM patching, render-mode
re-instantiation, router URL ownership, and focus across shadow DOM are all
real, Blazor-specific integration risks a synthetic DOM test can't fully
stand in for. This is a minimal, real `dotnet new blazor` project
(`StudioHost/`, .NET 10 SDK — the latest LTS available when this was built;
check `dotnet --list-sdks`) that hosts the built Studio elements at
`/studio`, driven by `test/playwright/blazor-host.spec.mjs`.

This is a **de-risking harness**, not the console integration itself
(that's honua-console#324, Phase 3) — but the integration pattern it landed
on (see Findings below) is exactly what that later work should start from.

## Layout

```
harness/
  blazor-host-src/mount.ts        # the actual client glue (TypeScript, built by Vite)
  blazor-host/
    README.md                     # this file
    StudioHost/                   # the .NET project
      Components/
        App.razor                 # root HTML document; loads the built bundle
        Layout/MainLayout.razor   # nav chrome (NOT the Studio mount point — see Findings)
        Pages/
          Home.razor              # "/" — static landing page
          Studio.razor            # "/studio" — @rendermode InteractiveServer
          StudioSecond.razor      # "/studio/about" — plain static SSR
        RenderModeLab.razor       # interactive canvas-toggle + live clock (hazard 2 + 4 drivers)
      wwwroot/studio/             # GENERATED by `npm run build:blazor-assets` — gitignored
```

## Build and run

```bash
# From the repo root:
npm run build:blazor-assets                                   # Vite → wwwroot/studio/{mount.js,studio.css}
dotnet build harness/blazor-host/StudioHost/StudioHost.csproj  # scoped — never the whole solution/tree
dotnet run --project harness/blazor-host/StudioHost --no-launch-profile
```

Or, in one shot: `npm run build:blazor-host` (both build steps) then
`npm run test:browser:blazor` (build + the Playwright spec, tagged `@blazor`
so it's excluded from the default `npm run test:browser` run — that spec
needs the .NET SDK, which the default browser-smoke path doesn't require).

`test/playwright/helpers.mjs`'s `startBlazorHost()` runs the built app with
`--no-launch-profile` + `ASPNETCORE_URLS=http://127.0.0.1:0` (an OS-assigned
free port, like `vite preview`'s own port-0 behavior, so this spec's server
never clashes with any other Playwright spec's) and
`ASPNETCORE_ENVIRONMENT=Development` explicitly — see Findings for why that
last one is load-bearing, not cosmetic.

## Findings

Each hazard below: what the issue asked for, what actually happened running
it against a real Blazor Web App, and what the fix was. All four are
exercised by `test/playwright/blazor-host.spec.mjs`.

### Hazard 0 (not in the original four, found first): Production-mode static assets 500

Running the built host with `dotnet run --no-launch-profile` (needed for the
dynamic free port) also silently drops `launchSettings.json`'s
`ASPNETCORE_ENVIRONMENT=Development`, falling back to `Production`. In
Production, `MapStaticAssets()`'s precompressed-asset negotiation 500'd on
every fingerprinted asset (`blazor.web.js`, the scoped CSS bundle, even the
built `studio/mount.js`) on this machine's SDK/Kestrel combination — the
whole page failed to boot. **Fix:** `startBlazorHost()` sets
`ASPNETCORE_ENVIRONMENT=Development` explicitly alongside the dynamic-port
env var. A real console embed will have its own environment configuration
story; the takeaway for this harness is narrower — don't assume
`--no-launch-profile` preserves anything from `launchSettings.json` beyond
what you pass explicitly.

### Hazard 1 — element survives enhanced nav between two Blazor pages

**What happened:** it didn't, and not for a subtle reason — for a
fundamental one. Three placements were tried, each one moving the mount
point further from anything Blazor's render tree could plausibly own:

1. `<div id="studio-host">` declared inside `MainLayout.razor`, outside
   `@Body` (the "obviously persistent, Blazor never re-renders the layout
   shell for a route change" placement). **Result:** wiped. The div itself
   survived (same node), but every child `mount.ts` had appended into it was
   gone after clicking a same-page nav link.
2. Moved to `Components/App.razor`'s `<body>`, as a sibling of `<Routes/>`
   — App.razor is the ROOT HTML document component, rendered once per real
   page load and never re-rendered by either enhanced navigation or an
   interactive circuit, in theory. **Result:** wiped, identically.
3. Stopped declaring the container in Razor at all — `mount.ts` creates it
   purely client-side (`document.body.prepend(...)`), so it has no
   server-rendered counterpart anywhere for Blazor to reconcile against, not
   even a coincidental one. Went further and tried appending directly to
   `document.documentElement`, outside `<body>` entirely. **Result: wiped
   too.** A `div` with `position: fixed` visibly on-screen, appended to
   `<html>`, gone after one click.

Confirmed via Playwright's own navigation events that this is **not** a
full page reload masking the symptom (`framenavigated` fires; `load` and
`domcontentloaded` do not) — this is a genuine client-side DOM rewrite, and
empirically it appears to touch the entire live document, not a scoped
region, at least for navigation originating from an `@rendermode
InteractiveServer` page. `document`/`window` (and this module's own JS
globals) are untouched — only DOM nodes are at risk.

**What I had to do:** treat "stays mounted" as something to actively
maintain, not something a correct placement gets for free. `mount.ts`'s
`resync()` is idempotent (`mount()` only creates what's missing) and runs
on every navigation signal available:

- `document`'s `"enhancedload"` event (documented Blazor API) — fires for
  plain, non-interactive-circuit enhanced navigation.
- A same-tick custom event dispatched by a **blocking, non-module** inline
  `<script>` in `App.razor`'s `<head>` that wraps
  `history.pushState`/`replaceState`/`popstate` — necessary because
  `mount.ts` itself is a deferred `type="module"` script that runs AFTER
  `_framework/blazor.web.js`, and wrapping `history.pushState` that late
  silently never fires: `blazor.web.js` had already captured its own
  reference to the original function by the time the deferred module ran.
  The inline script installs the same wrap early enough to actually observe
  it.
- A `MutationObserver` on `document.body` (`childList: true, subtree:
  true`) that resyncs whenever `<honua-studio-app>` is found missing. This
  is the mechanism that's actually load-bearing: both event-based signals
  above fire at the moment navigation *starts* (the URL update), but
  Blazor's actual DOM rewrite for interactive-circuit navigation lands
  asynchronously, one or more ticks later — resyncing immediately on the
  nav event recreates the element just in time for the delayed rewrite to
  wipe it right back out. The observer reacts to the wipe itself, whenever
  it really happens, instead of guessing at a delay.

**What "survives" means now:** not literal DOM-node identity — a real,
self-healing remount, verified as clean rather than merely present: the
Playwright spec asserts exactly one remount per navigation (not a retry
storm), a **different** `data-mount-token` (proving it's genuinely a new
instance, not a stale assertion), the session correctly re-injected on that
new instance, and — this is the part that actually matters —
`HonuaStudioCanvasElement.instanceCount` back to exactly its pre-navigation
value, proving the OLD instance's `disconnectedCallback` (ResizeObserver
disconnect, listener cleanup) fully ran rather than leaking alongside the
new instance's `connectedCallback`. A console embed inheriting this pattern
gets a stronger guarantee than naive persistence would have: the element
contract's cleanup discipline (`docs/element-contract.md` § "Mount/unmount
cleanup") is what makes frequent, silent remounts safe rather than a slow
leak.

### Hazard 2 — render-mode re-instantiation doesn't leak or double-register

`RenderModeLab.razor` (an `@rendermode InteractiveServer` component embedded
on `/studio`) toggles a plain Razor-declared `<honua-studio-canvas>` in and
out of the DOM via `@if (_showCanvas)`. Unlike hazard 1's mount point, this
element genuinely IS part of Blazor's own render tree — a normal
conditional render — so it behaves exactly as expected with zero special
handling: `HonuaStudioCanvasElement.instanceCount` goes up by exactly one on
add, back down on remove, across repeated cycles, with no drift. This is the
control case: it confirms the leak-proofing lives in the element's own
`connectedCallback`/`disconnectedCallback` discipline
(`src/elements/studio-canvas-element.ts`), not in anything specific to how
it got mounted.

### Hazard 3 — router URL ownership handoff

Working as designed once hazard 1's self-healing landed: clicking
`<honua-studio-app>`'s own internal "About" link (`routing-mode="host"`)
dispatches `honua-studio-navigate` and does **not** touch
`window.location` — confirmed directly (the URL is unchanged immediately
after the click). `mount.ts`'s listener is what actually calls
`window.Blazor.navigateTo()` — the same public JS API Blazor's own anchor
interception uses internally, not a private one. Blazor's router then
performs the real navigation (to its own `/studio/about` route, with the
`base-path="/studio"` re-prefix proving the round trip actually went through
Blazor and back), the self-healing remount from hazard 1 rebuilds the
element against the new URL, and `current-path` (stripped back down to the
element's own `/about`) renders the matching internal route. One bug
surfaced and got fixed here, not a Blazor hazard but a real element-contract
bug: `HonuaStudioAppElement`'s `currentPath` **property** setter used to
normalize and write internal state directly, without applying the same
`base-path` stripping the `current-path` **attribute** path already did —
so every resync silently un-stripped the path back to its raw host form and
the element always rendered its home route. Fixed by making the property
setter delegate entirely to the attribute (`src/elements/studio-app-element.ts`),
so there's exactly one place base-path stripping happens, not two that can
drift apart — see `test/elements/studio-app-element.test.ts`'s `base-path`
coverage for the regression test.

### Hazard 4 — focus is not stolen by an unrelated interactive-server DOM patch

Passed without needing any fix, which is itself useful signal: focusing
`<honua-studio-chat>`'s composer input (nested two shadow roots deep —
`<honua-studio-app>`'s own shadow root, projecting a light-DOM
`<honua-studio-chat>` child that has its own shadow root in turn) and then
waiting through several `RenderModeLab`'s live-clock re-renders
(`StateHasChanged()` on a completely unrelated part of the same interactive
circuit) never moves focus. This is `HonuaStudioElementBase#setShadowHtml`'s
focus-capture/restore doing its job — worth noting explicitly because
Blazor's own `<FocusOnNavigate Selector="h1" />` (`Components/Routes.razor`,
template default, left as-is here) DOES deliberately move focus to the
destination page's `<h1>` on a real ROUTE navigation, which is correct
accessibility behavior on Blazor's part, not a bug — this spec drives the
hazard through an unrelated interactive re-render instead of a route change
specifically to avoid conflating the two.
